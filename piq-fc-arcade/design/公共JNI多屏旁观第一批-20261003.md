# 公共 JNI 多屏旁观：第一批

2026-10-03，像素匠（Codex root 与协作代理）。源码基线 `cb8c14d`，工作分支 `codex/jni-multi-watch`。本文件记录实现和候选验证，不是稳定发行或安装通知。

## 范围与调用方式

本批只做多屏旁观：公共 Watch 租约、逐源客户端资源、真实四槽预算，以及街机、FC、SFC、MD 的适配。原开局选档→是否允许第二玩家→加载／就绪、实体手柄／街机申请和保存归属不重写。Flash/PvZ暂缓。

| 场景 | 调用方式 | 第一批规则 |
| --- | --- | --- |
| 附近公开 JNI Netplay 多机 | 服务器 Watch + 原 Netplay relay；本机各开只读 JNI 副本 | 不上传旁观输入、不占操作席、不写档；不同源独立纹理与代次 |
| 操作A，同时看B/C | A原操作JNI；B/C只读JNI | A画面直接复用；只归还A旁观租约，不关闭B/C |
| FC普通手柄／光枪JNI | 公共观看生命周期 + FC既有JNI构造／协议身份 | 不换核心／保存命名空间；光枪仍由服务器权威射线和输入驱动 |
| SFC/MD/街机JNI | 可信附属的原profile + 公共NetplayProcess | 不能按同机型全局participant排除旁观；保持各自内容授权 |
| MEDIA与历史独立进程Netplay | 旧媒体接收／进程链 | 本批仍单源，不与JNI多屏混合，不静默切换 |
| 主持离线／关闭 | 该源停止，其他源继续 | 无自动交接、无离线托管、无强加载 |

本机总原生上限仍为4，包括运行、加载预约和关闭未完成的核心。例如无其它JNI占用时可接最多4个只读源；自己运行一台通常余3槽。实际数量仍受已占资源、每房旁观额度、距离、附属支持和核心负荷限制，不承诺四台任何游戏都流畅。

已经操作的游戏不能被旁观挤掉；控制准备期间预留其尚未取得的槽。若四槽已被旁观占满，另开一台需要先释放一个旁观并等真正关闭后重试，本批未做异步自动腾槽。一个关闭卡住的核心继续计入占用，不能用解绑或完成UI关闭假报空闲。

声音优先操作会话；无操作时只播最近有效旁观源。音量按原机台与Minecraft设置计算，切换清旧缓冲。FC旧44100Hz单声道只在旁观呈现层转为48000Hz立体声，不更改模拟、校验或原主持音频。

## 公共接口及兼容

- `watch-3`：`Available(enabled, capacity)` 声明可保留旁观总数，不是空闲槽数量；0～4，不授予服务端权限。容量0仍可允许旧MEDIA，禁用则全部退订。主包客户端／服务端必须配套。
- `WatchLedger`按玩家、连接、源（source+hostLease）、token/revision管理多租约。各自心跳、超时、退避；来源不在退出范围、身份改变或连接失效只退对应租约。
- `WatchProvider.isParticipant(server, source, player)`新增精准源重载；旧附属默认沿旧全局判断，安全但不会自动获得多屏能力。
- `WatchClient.controlStarting(wire)`只退目标线；旧无参入口仍为保守清全部，不能在已适配公开路径乱用。主持需求缓存按源和主持代次分开，不能按provider覆盖同型另一台。
- `NetplayWatchContent.Preparation`沿原可信内容工厂。可选本地`ProcessFactory`保留FC特殊身份／光枪；只允许只读Grant，不能来自网络元数据，也不能改成操作授权。
- 只读内容下载与操作下载按精确请求和连接分离；公共ContentCard客户端只读最多4个token，服务端每玩家4个/全局16个，与上传和普通准备仍合计原64MiB在途上限；普通Runtime仍单实例。SFC受原服务端限频约束，复用4项有界串行请求及同hash读者共享，60tick重试间隔、最多3次；取消某读者不取消另一读者。同内容缓存并发写不再在Windows互相抢占原子目标。
- `NativeLibretroBridge.freeSlotsIfLoaded()`不加载DLL、不拿核心owner锁；`NetplayProcess.nativeSlotHeld()`按真实代次查询。它们是预算快照，最终原生reserve仍为权威，不扩大并发上限。

目录、ROM、核心DLL、保存格式、旧档和实体ID不迁移。附属依赖新的主包API，不能只替换附属而保留旧主包。

## 选型与不做内容

沿用公共Watch／JNI／Netplay，不新建编码器或每机型另一套旁观器。已查阅[Libretro官方Netplay资料](https://docs.libretro.com/development/retroarch/netplay/)的内容／核心匹配、旁观无输入和同步生命周期约束；这些资料不是本模组已通过多人性能验证的证据。此次不改上游核心或原生DLL。

下一批才考虑一人多主持（先小额度、每机独立保存／生命周期）；后续再评估低帧率预览串流和可选Opus。降低串流画面频率不等于降低模拟帧率。这些不作为本批成果。

## 安装与开发配套

适用 Minecraft 1.21.1 / NeoForge 21.1.236 / Java21；真实核心运行沿原 Windows x64 限制。主包与实际启用的附属需要服务器、参与客户端配套，依据是双方注册的 `WatchNetwork`、`SfcHomeNetwork`、`MdPublicNetwork` 及实体/物品注册，不仅来自依赖中的 `side`。服务端不因安装附属而自动托管这些客户端核心。

- 客户端与服务器均更新主包 `game-console-0.31.0-alpha.76.36.jar`；使用SFC、MD时分别换完整 `game-console-sfc-0.1.0-alpha.44.jar`、`game-console-md-0.1.0-alpha.12.jar`。替换同mod ID旧包，不并放两版；不能仅更新附属保留旧FC。
- 固定最新目录仍7个玩家JAR，街机1.5.5、GBA14、电脑11、PvZ11四包沿用原SHA，不把未改组件重新标为本轮制作成果。Flash仍不加入这组配套。
- SFC完整包包含 `piq_sfc_home` 与原 `piq_sfc_arcade` core9 两个ID；不另装薄包、core9或内部 `piq-retro-platform` JAR。
- ROM、BIOS和玩家存档不随包分发，不需要为本批迁移。MD Netplay DLL仍是MD11同一固定制品，完整对应源码 `genesis-plus-gx-piqnp1-source.zip` 已按原SHA复制至本批冻结目录另附，不放入mods；SHA为 `adeb3901c851c941fbeb07080aac3c49f64f4c3be5faf4d315cb1f015ea0b3fb`，许可限制不变。

开发先按根 `source-control/BUILDING.md` 核对固定输入，依次 FC `check jar`、SFC/MD `check jar`，使用配套主包。SFC开发薄包与既有core9按已审查的合并规则制作完整包：校验双方mod ID/版本、metadata语义合并、非metadata/manifest字节保持、再用根 `release_artifacts.py` 统一命名。不能直接运行历史core6/core7硬编码脚本冒充本期core9。

这里只给安装方法；本批不代换玩家/服务器实例，不执行线上发布、重启或GitHub推送。
