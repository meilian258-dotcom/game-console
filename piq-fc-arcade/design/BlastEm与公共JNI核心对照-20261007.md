# BlastEm 与公共 JNI 核心对照

2026-10-07，像素匠维护组。用途：回答“是否必须自行编译核心、问题是否在公共桥、为何保留哈希校验”。本次只做隔离诊断，没有修改生产核心、默认模式、保存格式或公共桥，没有新 JAR。

## 结论

官方下载的 BlastEm 能通过现有公共 JNI 启动原创诊断程序，输出画面和声音，响应按键，并在正确的初始化时序下保存、关闭、重开恢复。不能再用“公共 JNI 必须搭配自编译核心”解释早期选择。历史自编译 BlastEm 与这次官方版本在本用例上的逐帧结果相同，但这不代表两份 DLL 完全等价。

同一份 DLL 交给独立最小 JNA 前端和公共 JNI，180 帧的逐帧视频长度、视频 SHA256、PCM 长度与 PCM SHA256 全部相同；每帧均有非空 PCM。这说明本用例没有发现 JNI 独有的音画或输入差异，**不是公共桥全面无问题的证明**，更不是全部商业游戏兼容性或 Minecraft 联机验收。

BlastEm 的重复序列化和恢复后音频仍有差异；最小 JNA 同样复现。严格比较存档全部字节不能直接等同于实际游戏不同步。需要核对核心状态边界、音频呈现和回放策略，不能通过忽略未知字段或关闭校验让测试变绿。

每次只运行一个核心，独立 JVM、空 system/save 目录。BlastEm 使用核心默认选项；GX 使用当前普通 MD profile 的七项固定选项和两个六键端口。两前端均按核心对应的 RetroPad 映射输入 A，不把 GX 与 BlastEm 的按键位强行视作相同。当前 MD 的专用 PIQ Netplay 核心不在这张普通核心对照表内，不把 GX 普通核心结果代替它的验收。

## 实际结果

| 检查 | 官方 BlastEm | 历史 BlastEm | 官方 GX |
| --- | --- | --- | --- |
| 最小 JNA 与公共 JNI 启动、音画、A 输入 | 均通过 | 均通过 | 均通过 |
| 同 DLL 两前端 180 帧逐项比较 | 全相同 | 全相同 | 全相同 |
| 按 A 写入 SRAM | 均通过，接口字节索引 0 | 均通过，接口字节索引 0 | 均通过，接口字节索引 1 |
| 连续序列化字节相同 | 否 | 否 | 是 |
| 恢复后重复 20 帧输入，共三轮 | 画面相同，PCM 不同 | 画面相同，PCM 不同 | 画面和 PCM 相同 |
| 仅恢复即时状态会回退 SRAM | 否 | 否 | 否 |
| 状态与 SRAM 落盘、关闭、新实例读回恢复 | 两前端通过 | 两前端通过 | 两前端通过 |
| 正常关闭与 JNI 槽释放 | 通过 | 通过 | 通过 |

每个用例含 90 帧预热、20 帧按 A、三次各 20 帧恢复重演，以及关闭重开后的 10 帧。视频按实际有效长度比较，PCM 按实际长度比较，不补零、不裁剪、不跳过未知字段。比较发生在 CPU 帧和 PCM 数据层，不包含纹理上传、光影、扬声器听感、网络延迟或 MC 会话权限。

这里的关闭重开在同一个测试 JVM 内完成：JNI 关闭并卸载库后创建新实例，JNA 执行 unload/deinit 后重新装载游戏，未强制卸载动态库。这不是整个进程重启或断电耐久性测试。恢复检查只证明 API 接受状态、SRAM 标记保持和后续 10 帧音画输出，没有与不中断运行的基线比对完整游戏进度。

SRAM 独立落盘并在重开时显式恢复。仅恢复核心即时状态不会恢复该程序的电池进度，所以“状态功能可用”不等于自动包含所有保存区域。GX 的有效 SRAM 长度会变化，探针只把已保存的有效前缀写入新核心已声明的容量，不修改生产保存规则。

## 保留的失败及原因

初版探针错误地把 GX 的 SRAM 索引 1 用于 BlastEm，报告了 `inputWritesSram=false`；原始内存转储显示 BlastEm 的第 0 字节确实写入 `5A`。第二版按各核心实际布局分别检查，没有改变游戏程序或放宽写入值断言。

第二版裸 JNI 探针首次查询 `retro_serialize_size()` 在运行 90 帧之后，BlastEm 缓存大小为 141716 字节；重新加载时在首帧之前查询为 141704 字节。公共 JNI 因严格长度检查拒绝该快照；最小 JNA 直接传给核心则接受。第三版沿用当前生产 `LibretroJniRuntime.load` 的做法，在首帧之前查询保存能力，初次与重开大小均为 141704，两份 BlastEm 的 JNI 冷恢复均通过。**第二版暴露的是不一致调用时序与桥的长度合同之间的差异，不能写成当前生产仍必现的故障。** 未修改或放宽公共长度校验。

历史源码 `genesis.c` 的序列化会继续执行 68000，直到进入可保存位置；`libblastem.c` 的序列化大小会缓存，并为可变内容留出余量。这是解释“序列化并非纯读取、调用顺序会影响结果”的源码线索，不足以证明此次官方 DLL 的全部对应源码身份，也不能据此直接排除差异字节。PCM 的差异尚未逐字段定位为某个滤波器或缓冲区缺失。

探针首轮有一次 Java 字段前向引用编译错误，修正后才执行原生测试。三轮共 18 次串行 JVM，前两轮日志和探针原文保留；最终第三轮六个组合全部退出 0。测试不在 Minecraft 进程中进行，没有载入玩家存档或更改生产 DLL。

## 群里几个问题的直接回答

**为什么当时没有直接下载现成的核心？** 早期流程确实自行编译了 BlastEm，但现存记录没有官方 DLL 先行对照来证明那是必要步骤。这次补测已经证明官方制品能经现有公共 JNI 运行该用例。今后默认先检索、验证可信官方制品；只有具体缺口需要时才维护补丁或自行编译。

**RetroArch 能玩，是否就证明公共桥写错？** 不能这样直接判断。需要同一 DLL、内容、选项、固件、保存初态及调用顺序对照。本次 JNA/JNI 对照支持“此用例没有 JNI 独有音画故障”，同时保留调用时序导致恢复被拒绝的反例。本机未运行 RetroArch 对照，群里的画面不替代同文件实测。

**为什么还校验核心哈希，读版本号不行吗？** 本次两份不同 DLL 都报告 `1.0.1-pre`，已经说明版本字符串不能唯一识别文件。哈希用于确认固定发行输入及联机二进制身份，版本号用于向玩家说明；两者用途不同。相同哈希也不是确定性证明，ROM、BIOS、关键选项、协议和实际回放仍要验证。普通单机的核心供应策略与联机匹配规则应分别解释，不把哈希当作游戏名，也不把自行编译当成必要条件。

## 本轮决定与证据

不恢复已退役 BlastEm，不替换当前普通 GX 或专用 Netplay GX，不迁移旧档，不解锁未实现模式。继续先完善现有 JNI Netplay 的业务生命周期，而不是重写公共 JNI。商业游戏兼容性、真实 RetroArch 同文件对照、MC 双客户端及弱网长测另行验收。

本地证据：`receipt.json`、`receipt-v2.json`、`receipt-v3.json`、`comparison-v3.json`，对应目录的 `probe.log`、状态和 SRAM；可复现测试代码为 `CoreABProbe.java`、`run.py`、`compare.py`，前两版以 `*-v1.*`、`*-v2.*` 保留。原始日志含维护机本地路径，不应原封不动作为面向玩家的公开附件；本报告可公开，不包含 ROM、BIOS、用户存档或私人路径。

本轮依据的官方文档为 [BlastEm](https://docs.libretro.com/library/blastem/)、[Genesis Plus GX](https://docs.libretro.com/library/genesis_plus_gx/) 和 [Libretro 核心接口与调用生命周期](https://docs.libretro.com/development/cores/developing-cores/)，阅读日期 2026-10-07。官方功能列表用于了解接口与能力，不直接当作本模组 Netplay 验收。
