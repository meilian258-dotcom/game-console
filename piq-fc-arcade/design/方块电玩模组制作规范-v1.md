> 制作目标入口：[机器与附属通用制作规范](机器制作与交互标准.md)，第 1 节规定完整统一流程与设备类型分支；实际源码/API、界面、运行及保存差距查[全组件运行流程与复用接口总览](全组件运行流程与复用接口总览.md)。本篇只保留工程实施约束；距离与配置查[专项细则](方块电玩功能行为与配置规范-v1.md)，[SFC 蓝本](../../piq-sfc-home/design/以SFC为蓝本-附属制作说明.md)仅作历史接入参考，不另定一套玩家流程。

版本：1.0 · 2026-09-28 · 维护者：像素匠 / 方块电玩维护组。

**用途：以后无论谁制作方块电玩的新机器、新功能、新模型或新附属，都按同一套标准开发、检查和交付。** 不以某一种模拟器为主题，也不是只给新附属看的接口文档。

适用范围：主模组、FC/SFC/GBA/街机/电脑等附属，方块与物品、模型与动画、界面、配置、联网、运行库、游戏内容管理、保存和安装资料。初版源码基线：MC 1.21.1 / NeoForge 21.1 / Java 21、主包 `0.31.0-alpha.76.15`；本文具体版本与接口限制须按其日期理解，当前实际能力查技术总览及源码。

配套：[功能制作说明模板](功能制作说明模板.md) · [功能制作验收清单](功能制作验收清单.md) · [附属能力声明模板](附属能力声明模板.md)（仅新增/改造运行后端时另填）。

本次是**规范文档交付**：不改变现有游戏行为，不表示所有历史功能都已满足规范，也不表示稳定公开 SDK 已完成。历史实现的缺口需单独登记、逐项整改，不能仅修改文字就标为完成。

## 1. 规范如何执行

- **必须**：本次新增/修改范围的交付底线；不满足时明确列出阻塞，不得标为合规完成。
- **应**：默认做法；确需偏离时，说明原因、风险与替代方案，进入评审。
- **可**：可选能力；不支持可以，但必须明确关闭入口或说明原因。
- **现状**：指定版本源码/文档中存在，不代表所有实机环境通过。
- **目标 / 待补齐**：后续要求，不能当成现有 API 或已完成功能。

新功能用模板记录“用户要什么、改哪里、不改什么、如何验收”。连续反馈按清单逐条追踪；后来的补充不能导致前面的要求丢失。用户改变方案时明确标记替代关系，旧记录保留历史，不能同时执行互相冲突的方案。

必须区分“开机、进入操作、退出操作、关机、观看、停止观看”；必须区分“界面不可见、没有操作玩家、运行器停止”。统一术语与行为含义，不强迫所有机型拥有相同功能。

## 2. 组件划分与代码规范

| 层 / 组件 | 负责 | 边界 |
| --- | --- | --- |
| 主模组 | FC及公共设备、电视、机柜、权限/会话基础设施、公共界面 | 不把某附属私有规则当成所有设备规则 |
| 公共库 `piq-retro-platform` | 纯输入/帧接口、通用桥、存储与工作区基础 | 不反向依赖FC/SFC/街机实现，不访问MC世界对象 |
| 附属 | 自己的设备/核心适配、内容格式、输入映射、能力、保存与资源 | 复用公共入口，不复制平台类或另造绕过权限的通道 |
| 客户端展示 | 模型、动画、界面、音画与本机交互 | 不成为服务器权限或扣物品的权威来源 |
| 服务端规则 | 真实玩家/设备/席位验证、配置、持久化、网络授权 | 不加载客户端类；不因有人在线就广播所有重型数据 |
| 后台运行器 | 文件/核心/音画生产等耗时任务 | 不直接读写MC世界，不把任意网络数据作为命令执行 |

- 公共问题应修公共层，机型差异用明确配置/策略/能力表示。不得为每台机器复制一套开关、下载、旁观或保存逻辑。
- 共用组件先读调用说明，尊重维护者边界；必要扩展明确接口、调用方和回归范围，不随意改其他组件内部。
- 公共库只随主包提供一次，附属不重复打包公共类/worker。保持“主包含FC，其余按需附属”，不增加玩家必须另装的平台MOD。
- 服务端、客户端、纯逻辑和worker边界清晰；共享逻辑优先可独立测试。不得用反射/Mixin访问私有实现来绕过正常扩展入口或授权。
- 新字段、包和类按职责命名；避免含义不明的布尔组合、重复常量及新功能散落在无关类中。注释解释约束、线程、身份和失败处理，不只复述代码。
- 新资源/后端使用独立命名空间；旧方块、物品、后端ID不重命名重用。注册ID、发行文件名、显示中文名是不同概念。
- 不顺手重排无关代码、格式化全仓库或覆盖其他人的未完成修改。现有公开类不等于稳定外部API。

### 2.1 新功能先查现成方案（2026-09-30 补充）

**每个新附属的必做开工检查**：阅读核心官方文档、公共层说明与相近附属的调用合同 → 检索仓库复用入口及可信上游现成方案 → 在功能说明 2.1 留下日期、链接、比较和结论 → 才开始实现。不能以“上次查过”免除新机型核对；检索不可用须写明缺口，不写“没有方案”。验收清单 R05 未通过时，不得标为规范合规完成。

开始新增机器、运行后端、工具或公共能力前，必须先检查仓库公共实现和调用合同，再检索官方文档、成熟上游项目及官方预编译制品。已有功能的小修可注明沿用原方案；不要求为了小改动引入新依赖或重写架构。

- 在功能说明中记录日期、候选/版本、官方来源、适用平台/架构、许可证与分发要求、现成制品、公共接口匹配程度、必要适配和维护成本。采用/不采用均写具体依据，检索失败或未实测明确标注。
- 默认复用满足要求的现有组件与可信固定版本制品；自编译上游不是重写模拟器，但须说明为什么现成制品不能满足需求。补丁或自建需有明确缺口/缺陷证据，保留最小差异与回归方法，不能仅以“方便”或“可控”代替比较。
- 原生核心额外核对 ABI、软件/硬件视频、音频采样率/时序、端口/输入、SRAM/RTC/状态、多实例和所需联机模式。Libretro core-info、扩展名和官网能力表是候选元数据，不是本模组验收结果；最小隔离验证仅在任务授权范围内执行。
- 官方 nightly 的 latest 链接只用于发现候选；实际使用固定来源、版本/提交、SHA及必要对应源码和许可，不随下载目录更新静默升级，不执行游戏或群消息提供的任意核心。
- 替换核心先声明配置、同步身份、保存兼容与回退方案；不能只换文件名或绕过旧 SHA 校验。旧完整状态不可假定跨核心兼容，SRAM迁移也须验证并保留原件。
- 必要的 MC 交互/权限/展示适配与模拟器实现分开描述。找到了现成核心不表示卡带、电视、菜单或 Netplay 自动接通；现有模组缺口不能伪装成必须自研核心的理由。

此规则用于后续选型，不授权批量换核心、删除历史代码或重编已交付制品。

## 3. 模型、贴图、图标与实体交互

### 3.1 外观与资源制作

- 风格遵循现有机型：比例、材质、细节密度与MC世界一致。修改已有模型尽量保留结构，只改目标部位；交付可编辑源文件、贴图与游戏实际使用资源的对应关系。
- 模型必须有明确原点、朝向、缩放与占地；屏幕面、开关、插口、摇杆等关键坐标应集中定义或由共同几何来源导出，不让渲染与交互各猜一份。
- 游戏屏幕贴合实际屏幕面，避免悬空、穿壳、闪烁、镜像、过度拉伸；保留原始比例、旋转元数据与可选择的展示策略。横/竖屏不靠整体转柜子解决。
- 图标在物品栏尺寸下必须可识别，统一视角和合理大小，不裁边、不细小成一条线、不显示空白灰片。手持、地面、物品框和物品栏视角分别检查。
- 新贴图/音效/字体/模型须有来源与许可。导出的自动预览是辅助证据，不能冒充MC实机截图。

### 3.2 命中、选择框与动画

- 选择框、碰撞体、操作命中区域分别设计：选框清楚简洁，碰撞符合实体，按钮可点；不能为贴轮廓生成一堆难看的可见阶梯线。
- 小按钮允许合理交互容差，但不可越过真实墙体、机壳、邻柜或领地保护。邻机的选框空白不能错误挡住可见按钮；服务端仍须验证命中和距离。
- 每个新机型必须检查四个水平朝向、并排/贴墙/角落、多方块占地、相邻设备、主副柜。旧机器不应仅因资源更新就要求拆除重放。
- 开关位置/通断姿态/红灯/音效与权威电源状态一致；声效只在一次成功操作时触发，不因状态同步、拒绝请求、进入旁观而重复播放。
- 摇杆、按钮、扳机、插拔等动画反映实际席位与动作；松开回中，旁观可见，不把1P动画套到3P或另一机器。
- 线材走向、插头位置与功能一致，不穿屏幕、不悬空拖拽视觉；插拔/解绑/退还物品须一并验证。既有街机采用背部底沿走线，电脑键鼠采用接收器方案；不可擅自恢复旧方案。
- 既有街机开关以FC76.15对应三机型的正面左下方案为准，保留小翘板/亮灯/音效。后续新增同类机型应保持操作习惯；其他设备的位置按其明确设计，不一刀切。

## 4. 操作与生命周期

必须分别管理设备电源、核心运行、操作席、旁观和画面可见性。完整流程、适用选档/加入的先后、取消、失败和保存完成条件统一执行[通用制作规范第 1 节](机器制作与交互标准.md)；本节只补线程、身份和资源安全约束，不再由每个附属自行决定业务顺序，也不把流程阶段当成已经存在的枚举/API。

- 交互保持“有明确目标才执行”：空手右键、Shift、工具、手柄取还和菜单的职责要一致，避免无意弹调试页或触发另一动作。操作说明与实际绑定同步。
- 正常关机保留所选游戏和有效设备设置，再开机无需重新进游戏库选 ROM，但仍走该类型适用的检查、存档与加入确认链，确认完成后才启动；首次未选、文件缺失、核心故障等应提示真实原因。
- 退出操作只释放该席，是否整机关机由设备策略决定。多人中一人离开不能清空别人的输入；无按键/看过场不算退出。
- 每次启动绑定设备、世界、连接与会话代次。关机、换服、换游戏、卸载或新启动后，旧异步回复失效；旧清理不得关闭新会话。
- 文件读取、解压、哈希、进程启动/等待、大状态序列化不得阻塞MC主线程或渲染线程；后台任务有超时、取消和队列上限，核心由其拥有线程调用。
- 停止必须可重复调用而不重复扣物品、损坏存档或误关新会话；按序撤销输入/租约、停止生产、保存并回收进程/线程/音频/纹理/锁。
- 断线、死亡、切维度、卸载、核心崩溃、磁盘满都需明确处理。不自动承诺主持迁移、无人离线托管或强加载区块。

### 当前街机规则是一个策略，不是所有机器的统一默认

[FC76.15现行街机规则](街机全服规则-FC76.15-使用说明.md)：OP管理终端统一覆盖新旧街机；最后一名操作者主动右键退出可立即关机，默认关闭；独立空席倒计时0～3600秒、默认60秒，0禁用；两项关闭即不自动关机；再入席取消计时，安全结束保留。

新街机应复用同一策略，不复制一套附近玩家扫描。空席由占席事件维护截止时间，低成本检查到期；不新增每台机器每秒扫描全服玩家。家用机、掌机和电脑规则若要变化必须另有明确需求，不能因复用接口被一起改变。

## 5. 权限、物品事务与配置

- 服务端最终检查玩家真实连接、在线状态、设备/维度/距离、席位、保护规则与操作权限。客户端按钮隐藏/变灰不能替代检查。
- 管理功能按服务器OP/权限要求验证，打开界面后撤权也要拒绝。普通选游戏、占席、旁观、上传/下载、恢复存档和管理权限分开，不能统统授予控制者。
- PGM/DIP等维护入口不能借普通输入绕过OP限制；具体菜单持久化是否支持要独立声明，不能把“能打开”写成“已保存到机器”。
- 扣除/退还线材、银币、卡带或配件以服务器事务为准，防重发、双击和断线重复执行；失败不吞物品，成功不重复返还。付费投币边沿不能被普通输入清理丢掉或重放成多币。
- 配置明确属于全服强制、设备、核心还是客户端显示偏好，写清默认值、范围、保存位置、生效时机与优先级。
- 全服强制设置必须对旧设备生效，单机旧NBT/客户端不能盖过它；只设新机默认的功能必须明确写“新机默认”，二者不能混淆。
- 修改配置验证非法值、并发编辑、过期修订、运行中修改和旧数据迁移。不扫描全世界或强加载区块仅为更新一份公共规则。
- 玩家游戏资料、管理员公共标签、机柜运营配置和玩家进度必须分开，不能修改显示名就换错存档或影响其他机器。

## 6. 网络、渲染与性能

| 概念 | 必须区分的含义 |
| --- | --- |
| 操作距离 | 能否合法控制，不随显示范围任意扩大 |
| 观看范围 | 是否取得观看租约/订阅，不是全服广播 |
| 显示距离 | 是否绘制/上传游戏画面，不决定电源 |
| 音频距离 | 音量衰减与播放策略，不等于核心是否运行 |
| 自动关机 | 席位/计时/主动退出等设备策略，不以看不见为依据 |

- 普通100格外玩家不能仅因在线就接收街机音视频、ROM或状态流；MC区块基础信息和全服小配置可能仍同步，不能宣传“远处绝对零数据”。
- 超出显示范围停止无用的纹理创建/上传/绘制；退出观看撤销订阅。当前客户端若仍为附近其他玩家主持，必要核心计算和发送不得被自己不看屏幕的条件停掉。
- 当前原生街机显示/旁观默认16格，退出缓冲4格；新设备按明确的公共策略接入，不把临时调试距离写死在多个位置。
- 用事件、缓存和有界调度减少重复工作；不每帧扫目录/算文件哈希/创建纹理，不为每台机器重复全服遍历。也不能无依据声称“零占用”。
- 帧、音频、状态、下载、上传、并发核心都有大小/数量/超时/带宽预算；过载丢可替换旧帧或明确降级/拒绝，不无限排队。
- 本地、串流、服务端托管、本地同步、Netplay、只读旁观、原生通讯联机分开声明与验证。有即时存档或能本地多人，不代表确定性联机可用。
- 同步验证核心、内容、固件（如需要）、关键选项和协议身份；不匹配明确拒绝或请求切换模式，不能静默混跑。
- 观众不能取得控制/投币/保存/管理权限；换席撤销旧票据，旧观看清理不能撤掉新控制身份。
- 网络字段/长度/枚举均验证，协议变更有版本策略，截断、重复、迟到、越权消息安全拒绝。流量统计区分内容、音画、同步和其他数据。
- 性能验收记录环境、设备数、操作/观众数、时长、CPU/内存/流量/FPS；近处、远处、无人看、多机并行分别检查。

## 7. 目录、游戏内容与保存

- 复用 [ConsoleStorage](../../piq-retro-platform/src/main/java/cn/piq/retro/storage/ConsoleStorage.java) 的实例/世界 `game-console` 根；正式内容、缓存、临时运行目录、配置和保存分开，附属只管理自己的子目录。
- 临时工作区使用 [RuntimeWorkspace](../../piq-retro-platform/src/main/java/cn/piq/retro/storage/RuntimeWorkspace.java) 的所有权/锁/进程身份约束。不得宽泛清空系统Temp、其他组件目录或玩家原件。
- 所有路径归一化并限制在授权根内，拒绝路径遍历、外部绝对路径、重解析点逃逸和恶意压缩成员；限制文件数量/总量/解压膨胀/超时，不能只信后缀。
- 内容哈希/版本用于识别游戏，文件名和显示名不能独自作为身份。本地/服务器来源明确标注，服务器列表和下载都受权限约束。
- 大内容不能无界塞进单个内存数组或网络包。续传、离远继续下载分别验收，按可信内容身份校验分块；旧连接下载完成不能启动新世界中的设备。
- 不捆绑未授权商业游戏或BIOS；用户提供内容的权限与服务器分享权限分开，不能默认广播私人文件。
- 保存能力分别列出SRAM/RTC、记忆卡、即时状态、运营配置/NVRAM、核心选项；不能只用一个“支持存档”概括。
- 保存归属写清个人、介质、机柜、世界或共享会话；说明保存时机、写入者、切游戏/换核心处理。格式兼容身份包含必要的系统/核心/内容/选项版本。
- 使用原子替换、可恢复备份与同一目标并发写保护。坏档、磁盘满、权限拒绝或未初始化状态不能覆盖原好档；迁移先复制校验、冲突停止、原件可恢复。
- 当前大ROM续传与PGM按机柜持久化是独立未完成事项；本文只规定实现时的标准，不把需求当成果。

## 8. 界面、文案、图标与物品分类

- 沿用公共界面布局、按钮/输入框和提示组件，不为每个附属另造一套不一致菜单。用户界面优先清楚的中文名称，技术ID放详情/诊断，不要求玩家理解协议名。
- 当前游戏名、文件来源、运行模式、电源、操作/旁观状态表达一致；自动关机的立即规则和倒计时分别说明，0的含义不能含糊。
- 不支持的功能隐藏或禁用并给原因；错误说明失败阶段、能否重试和下一步，不能只有“操作未完成”。详细日志不含凭据/私人内容。
- 长游戏名、中文、不同GUI缩放/分辨率、窄窗口、滚动和焦点都要检查；重要按钮不出屏，不把关键说明截断成无法判断。
- 保存成功/失败/并发冲突有反馈；取消不写入，未保存草稿有处理规则。不能点击开关后本地看似成功而服务器未生效。
- 创造列表按用途分组排序，保持主机、显示设备、街机、介质、外设、电脑配件、家具等类别清楚；不抢占原版分类位置。新附属接入公共排序，不各自随意插队。
- 退役测试物品可以退出正常创造/配方入口，但旧注册ID和世界迁移要先设计；不能为清理列表直接破坏旧世界。
- 文案、帮助、默认值与实际实现同步更新，历史说明显著注明适用版本，不让旧教程覆盖新规则。

## 9. 模拟器附属只是制作规范的一个分支

2026-09-29 最新制作政策：用户确认现有 FC/SFC/GBA/街机/PvZ/MD 全面迁移公共 JNI，光枪须适配，后续新增模拟器附属默认走公共 JNI。Flash/Java ME 不在本轮。能力有差异时先补公共桥或明确报告缺口，不能为默认化标注不存在的功能，也不能只改私人入口。范围、旧版本现状及验收见 [JNI 全面迁移](JNI全面迁移-范围与验收.md)。本条为制作要求，不是已交付实现；不强迫非模拟器程序使用 Libretro。

新增/改造运行后端额外填写 [附属能力声明](附属能力声明模板.md)。统一权限、保存、生命周期和界面，不强制所有核心走libretro或拥有相同能力。

当前帧契约必须遵守：逐行未旋转 `0xAABBGGRR` 像素，48kHz双声道交错有符号16bit PCM；比例为原始显示宽高比，旋转为顺时针0～3个四分之一圈。显示层旋转/比例倒置只做一次。数组发布后生产者不再修改，消费方只读；当前 `RetroFrame` 每边最大2048。

数字按键必须正确转换核心掩码，逐端口释放不能影响别人。模拟轴、触屏、震动、换盘、GPU导出等新能力须独立设计并验证；不是换个核心文件就自动支持。

当前通用 `load(byte[])` 为64MiB上限，`fullPath=true`不等于任意大文件路径API；[游戏清单](../src/main/java/cn/piq/fcarcade/cabinet/CabinetGameManifest.java)现有最多5文件/单个64MiB/合计128MiB并有白名单；[通用worker](../libretro-generic-helper/src/main/java/cn/piq/retro/worker/GenericLibretroWorker.java)尚无通用硬件渲染/VFS/模拟轴等桥。新能力需版本化扩展和资源预算，不能仅删除边界校验。

每个核心固定来源/版本/平台/SHA和许可；独立进程不是OS安全沙箱。玩家或服务器内容不得指定任意DLL、命令或下载后执行文件。后台捕获连接与设备身份，迟到结果不能跨会话生效。

## 10. 兼容、测试与交付

### 10.1 兼容

分别管理规范版本、主包/附属兼容范围、网络/worker协议、核心版本和保存格式。规范v1不是稳定Java API v1；声明的版本范围与实际验过的组合分开写。

旧NBT缺字段使用安全默认；旧ID、文件、配置迁移有说明和回滚方案。未知版本/枚举/能力可诊断地拒绝，不重排枚举悄悄改协议。两端须同时升级的变更必须写清，不让用户猜安装在哪端。

### 10.2 分层验证

1. 静态/单元/契约：参数边界、状态变化、授权、序列化、异常与回归。
2. 集成/实际运行器：真实核心、进程、音画、存档往返和清理。
3. MC实机：模型/交互/GUI/声音、单机和专服多人、旧世界及相邻设备。
4. 稳定性/性能：重复启停、远近切换、弱网、长时、多设备、资源曲线。
5. 干净环境与人工验收：按文档从零构建/安装/复现，用户确认对应版本的实际范围。

按功能选择适用层级；纯文档不需要伪造游戏测试，纯模型也不能只凭编译成功就说视觉通过。使用 [验收清单](功能制作验收清单.md) 逐项写证据，未测写待验证。

**自动测试通过、独立进程通过、MC实机通过、人工验收、稳定发行是五件事。** 不互相替代；新增版本不能自动继承旧版人工通过。测试素材只使用有权使用/分发的内容，公开CI不夹带受限游戏。

### 10.3 每次交付必须说明

- 完成了哪些用户条目，哪些未完成/被新要求替代，是否需要重新放置设备或升级双端。
- 成品版本/路径/哈希、源码对应关系、前置依赖、客户端/服务端安装要求及依据。
- 新配置入口、默认值、范围、迁移/备份步骤、已知限制和实际验证范围。
- 保留旧成品/文档/人工记录；无新构建就写明，不把旧包当本次新包。
- 按工作区要求更新维护手册、开发工作台和适用的本地管理台资料。只写记录或构建不等于授权安装、线上发布、部署或重启。

## 11. 面向开源协作者的最低资料

新贡献应能让没有维护者环境的人理解和复现：README、组件边界、功能制作说明、开发环境/命令、必要公共接口、测试步骤、兼容组合、变更记录与许可资料。

公开构建不得隐含私人盘符、私有outputs、未提交旧JAR、凭据或预热缓存。依赖固定版本和来源，可提供校验清单/受控离线依赖；原生库要有对应平台、SHA、许可与适用的源码取得方式。

源码和文档使用可迁移的相对路径；公开包排除玩家档、ROM、未授权BIOS、私钥和内部登录信息。公共接口未来应提供版本清单、弃用规则、示例与契约测试；不要把内部 `public` 类当作永久兼容承诺。

当前框架确有共享能力，但尚未成为完整稳定公开SDK：能力声明仍分散、部分街机规则按后端ID特判、电脑程序固定分支、构建依赖部分本地历史产物。应独立整改并验收，**本规范没有替这些缺口完成实现**。

## 12. 后续修改如何遵守这份规范

开始：读取对应组件说明 → 列出完整需求与范围 → 检索已有实现/现成方案并记录选型 → 填功能模板 → 识别受影响规则/旧数据 → 登记工作台。

制作：优先复用公共组件 → 实现和测试同做 → 按实际进展逐条更新，不只完成最后一条反馈。

交付：检查最终文件与测试版本一致 → 说明已做/未做/待验 → 更新资料和维护记录 → 交用户验收；发布另行确认。

新功能按规范执行；历史问题按任务整改，不借规范擅自大改或删除。若规范与最新明确用户需求冲突，先澄清/记录新决定并更新受影响条款，不能让过期规范覆盖新要求。
