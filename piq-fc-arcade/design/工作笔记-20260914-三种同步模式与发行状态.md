## 3. 三种模式：建议保留，但不是三份模拟器同时跑

| 方式 | 运算位置 | 性能/带宽取舍 | 当前边界 |
| --- | --- | --- | --- |
| 玩家本地同步 | 每位参与者各运行一致核心；服务器排序输入、校验、缓存状态 | 服务器运算较少，玩家承担模拟和状态校验；通常省视频流量，仍有快照、加入/恢复和旁观流量 | FC/SFC 有不同路径；Native 实验仅固定核心与已验证游戏，不是全街机通用 |
| 玩家托管串流 | 主持玩家运行一份核心并编码，服务器转发 | 主持端承担模拟+编码和上行，接收端解码；服务器出口随人数增长 | 当前依赖真实 host 玩家，离开可能结束整局；远端画质/帧率/响应不同于主持端 |
| 服务器托管串流 | 服务端每局运行一份核心并编码，客户端只解码/显示/播放音频 | 客户端无需运行这一局的核心；服务器承担每局 CPU、内存及每接收端出口带宽 | 尚未实现；需要新的服务端执行权限、工厂、资源/存档上下文、生命周期和隔离 |

- 服务端运行会生成完整 framebuffer / PCM，客户端“渲染”指上传屏幕纹理并显示，不是服务器只传按键就能让不运行核心的客户端凭空生成画面。
- 服务器托管能去掉对启动者电脑的运算依赖，但不消除按键上传、编码、传输、显示延迟；并不保证比本地同步更跟手。
- 同一个人观看同一局的两块屏幕，应复用一次接收/解码结果；两台串联街机共用一个会话与核心，不应各跑一份。不同机台独立玩不同局才增加核心实例数。
- 四人是同一核心的多输入端口，仍要求游戏/核心支持；不代表模拟真实街机硬件串口，也不代表 GBA 通讯联机已实现。
- 服务器托管可以设计为 P1 离开仍继续，但需要明确剩余席位、最后一人离开、存档所有权、关机权限和超时策略，不能仅改一处退出判断。
- 本地同步不等于完整回滚预测方案。本轮未实现自动 host 迁移、服务器权威加客户端预测，或运行中无缝迁移状态。

## 5. 本地同步开销：必须区分家用 SFC 和通用机柜

下表是当前代码与既有真实核心测试样本的推算；不是当前成品公网抓包或所有 ROM 的平均值。

| 路径 | 常态输入/校验 | 完整状态 |
| --- | --- | --- |
| FC 锁步（含家用 FC） | 按键变化上传；服务器约 60 个小模拟帧/秒；画面摘要约每 300 帧 | 主持端约每 4–5 秒响应快照请求；自身为压缩 delta，大小随状态变化 |
| 家用 SFC 独立路径 | 输入同步；每 600 帧本地 checkpoint 并发送小摘要，约 10 秒 | 加入/修复收到请求后才上传、恢复；不能算成平时每 5 秒上传 1.29 MB |
| 通用机柜 SFC LOCAL_SYNC | 输入变化、保活、权威帧批次；每 300 帧 saveState + SHA | 主持端每 300 帧完整快照上传服务器缓存，约 5 秒 |
| Native NeoGeo LOCAL_SYNC 实验 | 同通用机柜；每 300 帧仍完整 saveState + SHA | 主持端每 1800 帧上传，59.1856 FPS 下约 30.41 秒 |

量级和限制：

- 通用机柜输入包裸字段常约 36–39 B，约 20 个权威批次/秒、每批约 48–55 B；FC 下行小帧约十几 B × 60/s。纯输入下行约 1 KB/s 量级，未计 Minecraft/TCP/IP 包头、摘要、快照等。
- SFC 旧核心样本状态 1,294,513 B；按通用机柜每约 5 秒上传计算，主持端上行/服务器入站约 259 KB/s，即约 **2.07 Mbps**。样本来自 `piq-sfc-home/design/repair19-core-source-v1.json`，报告明确未启动 Minecraft/socket。
- Native 旧核心样本完整封套 3,334,266 B；每约 30.41 秒上传计算，主持端上行/服务器入站约 110 KB/s，即约 **0.877 Mbps**。样本来自 `piq-native-arcade/design/native-snapshot-sync33/boundary-source-v4.json`。
- 上述周期快照通常只缓存到服务器，**不会每个周期广播给所有参与者**。中途加入、校验分歧或修复时才有完整快照下行。
- FC `design/zapper-session26-final-v2.json` 旧测试夹具快照 8,595 B，不是所有游戏平均值；协议最大快照 2 MiB 也不是实际常态大小。
- 本地同步下通用机柜仍可为旁观者发送音画；参与者无需接收视频，不等于整个房间没有串流。
- Native 当前实验本地同步只支持固定 KOF97 / Metal Slug 2 配置、核心/ROM/BIOS 校验及最多两席；媒体模式多席能力没有因此自动变成本地同步四人验收。

主要实现入口：

- `piq-fc-arcade/.../client/cabinet/CabinetSyncWorker.java`：每 300 帧 checkpoint、SHA，host 按核心配置周期发布快照。
- `piq-fc-arcade/.../cabinet/CabinetSyncCore.java`：默认快照周期 300，NativeProfile 改为 1800。
- `piq-fc-arcade/.../cabinet/CabinetSynchronizer.java`：上传验证后缓存；加入/摘要不一致/请求恢复才下发完整状态。
- `piq-fc-arcade/.../client/cabinet/CabinetClientBackends.java`：本地同步参与者与旁观媒体路径并存。
- `piq-fc-arcade/.../server/ServerArcadeSessions.java`、`core/wasm/WasmNesCore.java`：FC 请求快照和压缩实现。
- `piq-sfc-home/.../client/SfcPlayback.java`、`SfcRepairClient.java`、`server/SfcRepairLedger.java`：家用 SFC 摘要/按需修复。

以上 `...` 仅省略 Java 包路径；不是字面文件名。按类名定位，避免把家用和机柜路径混为一谈。

## 6. 串流开销：代码事实、算例和未知值

当前通用机柜的 `CabinetMediaCodec` / `CabinetMediaStream` / `CabinetMediaPolicy`：

- 独立 RGB565 + zlib 视频帧，最高 384×288，每帧压缩数据上限 128 KiB，24 KiB 分片。
- 自动目标 20/30 fps，视频帧率不等于模拟器实际运行帧率；队列和预算不足会丢帧/降低目标。
- 48 kHz 双声道 PCM16 尚未使用专门音频压缩。持续音频原始载荷 `48000 × 2 × 2 = 192000 B/s`，即 **1.536 Mbps**；Minecraft 传输层可能另行压缩，不能称为抓包最低速率。
- 当前发送载荷预算补充率为 1 MiB/s，约 8.39 Mbps；这是应用层预算，不是公网精确限速，也不是常态实际速率。
- 自动策略在 `平均帧字节数 × 30 + 192000 > 850000` 等条件下退回 20 fps。

**解释用算例，不是测试成绩**：假设平均压缩视频每帧 20 KiB，30 fps，保持上述 PCM，则一条流 `(20480 × 30 + 192000) × 8 = 6.4512 Mbps`。

| 四位玩家同一局、无旁观者 | 主持玩家上行 | 服务器出口 | 每位远端接收者下行 |
| --- | ---: | ---: | ---: |
| 玩家主持串流 | 约 6.45 Mbps | 发给另三人，约 19.35 Mbps | P2–P4 各约 6.45 Mbps |
| 服务端托管串流（拟议） | 主要是小输入包 | 发给四人，约 25.80 Mbps | P1–P4 各约 6.45 Mbps |

- 每新增一位接收同局画面的观众，以上例再加一条下行流。不同游戏/画面复杂度、传输层压缩和包头、网络背压均改变实际数值。
- 不能把现有代码的 20/30 fps、PCM 成本或预算当作 RetroConsole 的实测速率。
- 没有测过指定服务器 CPU/内存配置下的托管性能，不承诺“每台固定占 5% CPU/100 MB”或能带多少台；需测每帧核心耗时、编码耗时、MSPT、丢帧、内存和出口。

## 7. 服务端托管可复用部分与隐藏工作量

- 可复用：纯核心接口（NesCore、SfcCore、RetroEmulator）、媒体编码/严格解码、分片、有界发送窗口、客户端屏幕和旁观播放。
- `CabinetRooms.input/media/validateLease` 当前把执行者绑定到真实 host ServerPlayer、Connection、port 0、机柜拓扑。须分离“执行核心者”和“拥有操作权限的玩家”，不能伪造 host 绕过权限校验。
- `SfcHomeServer` 和 FC `ServerArcadeSessions` 目前管理租约/时序/状态，不存在一个已可开启的服务端核心开关。
- GBA / Native 客户端 backend 捕获 Minecraft 玩家、连接、文件和存档上下文，不能直接把客户端类加载到专服；需要独立服务端工厂及上下文。
- `NativeProcessSession`、`GbaProcessSession` 有全 JVM 单 ACTIVE/ownedProcess 保护；要做服务端多局并发必须重新设计会话隔离和有界进程池，不能简单删除保护。
- FC/SFC WASM 较适合先做无界面验证，但实际专服类加载/资源加载/平台库仍需测；Native/GBA 当前 Windows 辅助程序不能直接当作 Linux 已支持。
- 模拟、状态复制、编码不能放 MC 主线程；独立线程仍争抢硬件资源。原生核心宜有独立 worker/进程、超时、取消、限额、有界队列和严格 ROM/状态校验；子进程隔离不等于完整安全沙箱。
- 同局编码一次、按接收者转发；同客户端多屏复用。无观众时不应白做旁观编码。最后一人离开如何暂停/保存要明确，不能让空机台无限后台运算。
- 建议先评估压缩音频、画面变化编码和关键帧恢复，优化重复数据；任何差分方案必须能在丢帧/重连后正确恢复。
- 快照优化须同时保留加入/恢复能力、有界输入历史与安全校验；不能为省带宽直接删掉快照，或只拉长周期导致历史耗尽。

## 8. 体积核查：三种模式不是三套资产

当前 FC 主 JAR 为 30,599,429 B（约 30.60 MB；29.18 MiB）。只读 ZIP 目录核查：

| 类别 | JAR 内压缩体积（约 MiB） |
| --- | ---: |
| Windows / Linux x86_64 Wasmtime 原生库 | 24.79 |
| PIQ 自有代码（全部功能，不仅联机） | 1.81 |
| 模型、贴图等 assets | 1.27 |
| 其他依赖与元数据 | 0.94 |
| FC core 目录 | 0.05 |

分类合计不包含 ZIP 目录/成员头的额外字节。最大两项：

- `natives/linux-x86_64/libwasmtime4j.so`：压缩 13,510,321 B，解压 41,216,320 B。
- `natives/windows-x86_64/wasmtime4j.dll`：压缩 12,484,172 B，解压 37,843,968 B。

配套包 `制作Mod/03-街机模拟/发行资源清理-FC38-配套测试包-20260914-v1.zip` 为 159,505,800 B（159.51 MB；152.12 MiB）。最大成员为外部运行库 ZIP：127,026,327 B，约占 79.64%；其次 FC JAR 30,599,429 B，约占 19.18%；其次 SFC JAR 1,292,224 B。以上内层文件已压缩，外层对应成员采用存储。

源码是**单独**的同名 `-源码.zip`，259,669,517 B，未嵌入上述 159.51 MB 测试包；不能说测试包主要被源码撑大。

结论与打包建议：

- 增加第三种模式主要增加执行/同步/权限代码，能够复用核心、模型、输入、音画基础，不应按模式重复捆绑所有资源。
- 不承诺具体新增 KB/MB：新增 Linux 原生核心、音视频编码库或依赖可能明显增加体积，编译后再核对。
- FC 继续一个主 JAR；附属按需安装，共用依赖不重复打包。对应源码/许可单独完整提供，不能以减体积为由省略义务。
- 保留三种模式不等于同时运行三份核心，每局只启用选中的执行方式；运行时缓存/私有暂存和多局内存是另外的容量问题。
