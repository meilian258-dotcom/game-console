# Libretro 官方文档：方块电玩接入笔记

阅读日期：2026-09-21。整理：像素匠，输入、Netplay、核心库专题由三个只读研究代理交叉核对。

用途：后续开发的长期参考，不是新增功能公告。以 FC64 通用软件桥为本地基线；本轮只研究和记录，没有改 MOD 代码、构建、安装、运行 ROM 或发布。

阅读范围：浏览官网主要目录，重点阅读开发接口、输入、音画时序、存档、联机、核心库、配置、排错和许可；不是逐页读完全部机型、平台安装教程及源码。文末记录具体入口。网站会更新，实际接入须以固定核心版本、对应头文件和运行验证为准；涉及现有 Netplay 实验时对照 RetroArch v1.22.2，不能把 master 新能力倒推到该实验。

## 1. 先记住的结论

1. libretro 是统一核心接口；RetroArch 是参考前端；libretro-common 是主要用 C 编写的公共构件库。我们可以做自己的 Minecraft 前端，不必把 RetroArch 的整套菜单搬进游戏。[开发概览](https://docs.libretro.com/development/libretro-overview/)、[公共库](https://github.com/libretro/libretro-common)
2. 统一接口能减少 SFC/GBA/街机重复桥接，但不能保证换一个 DLL 就可交付。每个核心的文件依赖、输入设备、选项、状态格式、平台库和许可仍要逐项处理。
3. 核心页面的 Netplay 勾表示相关支持，不是我们的模组已经接上网络功能。FC64 中真正的 RetroArch Netplay 仍仅为独立本机实验。
4. Saves（游戏原生保存数据）与 States（运行状态快照）不同；“个人存档／卡带存档”是我们决定归属的规则，不是 libretro 的原生模式。[术语说明](https://docs.libretro.com/guides/install-windows/#glossary)
5. 当前 API 也有 Netpacket 扩展，不能笼统说“libretro 完全没有网络接口”；但核心包通信、输入回滚、音画串流是三种不同机制，不能混为一谈。[固定版本接口](https://raw.githubusercontent.com/libretro/RetroArch/v1.22.2/libretro-common/include/libretro.h)

## 2. 本地实现基线：已经有的和真正欠缺的

本节来自本地源码与 FC64 指南，不是官网对我们项目的背书。

| 范围 | FC64 当前情况 | 后续用途／边界 |
| --- | --- | --- |
| 公共加载层 | `LibretroProfile` + `LibretroProcess`；可信资源与 SHA 固定，独立工作进程 | 保持公共契约稳定，让附属声明核心配置；不是任意 DLL 加载器 |
| 生命周期 | 加载、逐帧／批量运行、重置、状态保存恢复、关闭；单所属线程调用 | 复用基础桥；原生隔离只减少崩溃影响，不是安全沙箱 |
| 数字输入 | 标准 16bit RetroPad，描述符允许 1–4 端口 | 适合 FC/SFC/部分街机基础按键；不等于所有四人外设已接通 |
| 光枪 | Mesen 专用 subtype 262、port 1、Pointer/Mouse 路径 | 不能直接当作各核心通用 Lightgun 实现 |
| 软件音画 | 0RGB1555/XRGB8888/RGB565、重复帧、几何更新、FPS／采样率元数据、原始双声道 | FC 适配仍有自己的固定 NTSC、60 帧会话节奏和单声道处理；其他平台不能照抄 |
| 选项 | v0；报告 options version 0，读取固定键值／默认值 | v1/v2、分类、国际化与动态显示尚未接入；有 v0 回退的核心仍可能可用 |
| 原生保存数据 | 可读取 memory ID 0–3；没有通用 memory 写回协议 | 不能将“能导出 RAM”视为 SRAM/RTC/NVRAM 持久化闭环 |
| 目录／内容 | 内存或完整路径加载，持久扩展内容信息；系统/素材/保存目录都指向单会话工作目录 | 尚无独立固件供应、持久保存目录设计、VFS、多文件依赖与子系统加载闭环 |
| 元数据／诊断 | 部分提示、输入描述和控制器信息收到后仅确认，不传回使用；缺核心日志接口 | 需要完整能力说明和更具体的失败信息 |
| 旋转／硬件 | 只接受零旋转；不提供硬件渲染、模拟轴、震动、通用换盘或 Netpacket | 竖屏街机是优先补项；3D 等硬件核心另做专项 |
| 追帧优化 | 批处理和可选音画回传；子进程仍转换、缓存视频 | 目前主要省 IPC，不可宣传已经省掉全部模拟或渲染开销 |
| 联机 | Minecraft 现有三种公开方式保留；RetroArch 三端仅 loopback POC | 未接入 MC 玩家身份、席位、断线和保存流程 |

## 3. 核心接入：把可复用部分做成稳定公共能力

官方将前端与核心分工，并以 `libretro.h` 为主要接口依据；生命周期、输入、音画和可选序列化都有明确契约，API 不承诺多线程安全。[核心开发](https://docs.libretro.com/development/cores/developing-cores/)

我们的下一步设计建议：

- 用能力表表达“必须／可选／未实现”，加载前给出具体缺项，不用一个笼统“支持 libretro”开关。
- 为附属固定核心身份、平台二进制、内容类型、设备、选项和固件需求；版本化公共描述格式。只增加已覆盖能力的核心时，争取不要求改 FC；缺公共能力时仍可能需要更新主包，不能承诺以后永不更新。
- 按对应 ABI 核验 `bool`、`size_t`、结构体对齐、回调生命周期；继续让单一所属线程调用核心。跨平台不能只检验资源存在。
- 每个新核心首先运行独立烟测，再进入 MC；不要一开始就混入权限、网络和模型渲染，使失败无法分层定位。
- `libretro-common` 的文件流、重采样、哈希、线程等构件可按需评估；它不是现成 Java SDK，也不是 Netplay 独立包。引入其 C 代码应证明收益、核对实际文件许可，避免为已有 JVM 功能新增不必要的原生维护负担。[仓库目录](https://github.com/libretro/libretro-common)

## 4. 选项与界面：减少硬编码，也避免再次变复杂

新版 Core Options 提供更丰富的描述与分类；官方还提供核心选项翻译流程。配置、游戏按键映射和画面预设在 RetroArch 中是不同层次。[选项翻译](https://docs.libretro.com/development/cores/core-options-translation/)、[配置覆盖](https://docs.libretro.com/guides/overrides/)

建议先补 v1/v2/intl 读取与兼容回退，再按我们自己的产品规则显示：

- 普通玩家只看到常用控制、画面、音量和自己的保存选项；高级核心设置放调试界面，不照搬几百个 RetroArch 菜单项。
- 将“影响模拟状态的会话选项”和“纯本地显示／键位偏好”分开。区域、设备、超频等关键配置由会话统一，纳入状态身份；是否影响确定性需逐项验证。
- 开局冻结需要一致的选项；不允许玩家各自偷偷改动导致分歧。需要重启的设置明确提示，不在游玩中静默应用。
- 展示“当前值／默认值／下次启动生效”即可，详细说明按需展开；不要为每一步添加开发阶段说明。
- v2 回调的返回值有分类支持等特定语义；实现时不能把所有布尔返回都当“操作成功”。版本号没实现前不能虚报支持。[v1.22.2 API 头](https://raw.githubusercontent.com/libretro/RetroArch/v1.22.2/libretro-common/include/libretro.h)

## 5. 输入：统一 RetroPad，但保留两层映射

推荐分层：玩家键盘／实物控制器 → RetroPad → 核心与游戏动作。RetroPad 是虚拟控制器规范，不自带 USB/蓝牙驱动；RetroArch 的 autoconfig 和游戏专用 remap 是前端功能。[Input API](https://docs.libretro.com/development/input-api/)、[输入与映射](https://docs.libretro.com/guides/input-and-controls/)

应用到我们：

- F7 将基础键位与游戏专用映射区分；保留 N 的人物移动锁定以及退出、失焦时释放按键。
- 后续若接实物手柄，应显示已识别设备、玩家归属、按键预览；设备名称、VID/PID 和驱动会影响匹配，不直接照搬某份配置的按钮编号。[自动配置](https://docs.libretro.com/guides/controller-autoconfiguration/)
- 读取输入描述、每端口设备信息，减少 FC/SFC/街机各写一份按钮名称；但核心描述不能越过 Minecraft 服务端的席位授权。
- Mouse 的相对移动、Pointer 的绝对定位、Lightgun 的屏外／扳机和 Analog 的模拟量应分别建模，不能全塞进数字掩码。[Input API](https://docs.libretro.com/development/input-api/)
- Mesen 的 Zapper 文档使用 Pointer；四人适配器还涉及 User 5 配置。沿用已验证的 FC 特殊适配，扩展外设时重新验收，不因桥支持四路就宣布全部四人游戏可用。[Mesen 控制器](https://docs.libretro.com/library/mesen/#controllers)
- 震动、热插拔、多鼠标需要前端和设备支持；当前不能当作已完成。[输入驱动](https://docs.libretro.com/guides/input-controller-drivers/)、[驱动规范](https://docs.libretro.com/development/retroarch/input/input-drivers/)

输入验收建议：四角／中心／屏外坐标、旋转后瞄准、连按组合、双人互不串键、失焦释放、热插拔、中途换人、观战不能注入按键。实物手柄尚未在本轮核实或实测。

## 6. 存档：原生保存、即时档、归属三件事分开

原生保存通常是游戏自己维护的数据；即时档是核心运行状态。序列化是可选能力，部分核心存在初始化、大小、会话或平台限制，不能从有 `serialize` 函数推导跨版本通用。[术语](https://docs.libretro.com/guides/install-windows/#glossary)、[开发指南](https://docs.libretro.com/development/cores/developing-cores/)、[接口限制](https://raw.githubusercontent.com/libretro/RetroArch/v1.22.2/libretro-common/include/libretro.h)

我们的设计建议：

- 保留玩家已确认的产品规则：个人档属于当前玩家；卡带档随该卡带走。公共核心层只提供数据能力，不自行决定共享、清理或覆盖。
- 在公共桥补受限的原生保存数据恢复和退出落盘闭环；有些核心通过内存区，有些通过保存目录文件，需要分别适配。重点核对 SRAM、RTC 和 NVRAM，不能只做即时档。
- 会话临时目录与长期保存目录分离，写入采用原子替换／备份；异常退出不能用空数据覆盖好档案。读写均受尺寸、路径和所属会话约束。
- 即时档继续记录 ROM、核心／运行配置、普通或特殊设备模式与格式身份。不把旧 WASM 档喂给 Mesen，也不以改后缀冒充迁移。
- 跨 OS 的二进制 SHA 天然不同：同平台可要求完全相同二进制；跨平台需要经过测试的对应构建／共同兼容身份，不能粗暴要求 Windows DLL 与 Linux SO 哈希一致。
- 不支持或验证未过的持久化能力，界面应明确禁用；不能显示“保存成功”却只留在待清理的临时目录。

验收应包含：退出核心进程再启动仍保留游戏内进度、即时档恢复、坏档拒绝、写失败保护、同 ROM 两张卡互不串档、同卡换玩家的两种归属规则、忙会话不可覆盖。

## 7. 音画：对卡顿和扩展机型最有价值的部分

开发指南要求读取核心音画信息，处理逐帧输出和交错双声道样本。Dynamic Rate Control 讨论以细微重采样调整应对音频缓冲与显示节奏漂移；该方法有适用范围，不能解决任意帧率差。[开发指南](https://docs.libretro.com/development/cores/developing-cores/)、[动态速率控制](https://docs.libretro.com/development/cores/dynamic-rate-control/)

针对本模组的建议：

- 分清核心 FPS、MC 渲染 FPS、服务器 tick 和音频采样时钟；不要统一硬编码为 60，也不要让每台电视独立争夺 MC 全局 VSync。
- 下一机型接入时真正消费公共 AV 元数据，包括采样率、宽高比与动态尺寸；先保证正确速度和音调，再谈优化。
- 音频输出维护有界缓冲，统计欠载／积压和实际延迟；如评估动态重采样，应限制在播放端，不任意改变联机核心的权威推进帧数。
- 追帧／回滚时仍执行逻辑帧，但只展示最后需要的画面、不重复播放过期声音。现有批处理只省 IPC，后续再评估核心支持的 A/V 跳过提示，逐核心确认不会改变模拟状态。
- 街机旋转需与宽高比、电视贴图和光枪坐标一起处理。当前零旋转实现是迁移竖屏内容前的明确缺项。
- 硬件渲染需要上下文/FBO等生命周期管理；独立进程里的显存对象不能直接视作 MC 纹理。FC/SFC/GBA 基础软件核心先稳定，硬件核心另开验证。[OpenGL 核心](https://docs.libretro.com/development/cores/opengl-cores/)

Run Ahead 依赖快速可靠的状态，并增加模拟开销；不是回滚联机的同义词。官方还解释双实例模式可绕开部分核心读档后的音频问题。我们已观察到 FC 读档声音瞬态，但这只能作为研究方向，不能据文档认定同一根因或已修复。[Run Ahead](https://docs.libretro.com/guides/runahead/)

建议先记录帧耗时、IPC字节、纹理上传耗时、音频缓冲和追帧次数，测多台机器及高刷新率/低TPS组合。不要直接把 RetroArch 的“低延迟”宣传数值当作 MC 内实测结果。[延迟选项](https://docs.libretro.com/guides/latency/)

## 8. Netplay：最值得借鉴，但必须单独接入

RetroArch 输入联机围绕帧编号、输入与状态运行，可预测并在需要时回滚重演；观众也是运行核心的一端，不等于接收压缩视频。[开发协议](https://docs.libretro.com/development/retroarch/netplay/)、[FAQ](https://docs.libretro.com/guides/netplay-faq/)

建议映射到 MC 的职责：

- 模组服务器仍负责玩家身份、开机资格、2P允许／拒绝、实体手柄借还和存档归属；Netplay 房间密码不能代替这些校验。
- 房间主持、1P、2P、观众分别建模；玩家离开席位不自动等于主持迁移。角色切换要有明确生效帧。
- 引入成熟联机实现时保留原音画串流用途：不能要求所有旁观者都具备本地核心算力，亦不能声称输入观战无需内容文件。
- 新玩家加入需取得合适状态并追赶；同步途中不应显示已进入可操作席位。
- 联机前主动核对内容、核心版本、关键选项与设备；同核心名字不够。官方建议一致的版本与内容。[FAQ](https://docs.libretro.com/guides/netplay-faq/)
- 一客户端申请多个设备的机制可以参考，但端口分配不能与默认自动分配混乱；端口数量也不是游戏人数上限的承诺。[多控制器](https://docs.libretro.com/guides/netplay-multiple-controllers/)

网络策略尚待设计：RetroArch 默认端口／大厅／Relay 不能直接复制成“每台 MC 电视开一个公网端口”。是独立授权通道、受控转发，还是封装入现有网络，需要考虑队头阻塞、带宽、保护、可达性和运维；本轮没有开放端口或调整防火墙。[连接指南](https://docs.libretro.com/guides/netplay-getting-started/)

重要分支：`SET_NETPACKET_INTERFACE` 用于核心定义的通信，和常规输入帧回滚模式不同；v1.22.2 明确区分两者。GBA 连接线模拟必须查具体核心、版本和通信实现，不能把第二只 RetroPad 当第二台 GBA。[模式定义](https://raw.githubusercontent.com/libretro/RetroArch/v1.22.2/network/netplay/netplay_private.h)

验收也不能只看“连接成功”：固定 v1.22.2 中，核心版本或内容 CRC 不一致可能仅警告；首次状态 CRC 校验失败还可能关闭后续状态 CRC 比对。这不表示所有协议或身份检查都被关闭。因此独立检查确认帧一致性，不能只数日志中有没有报错。[固定版本实现](https://raw.githubusercontent.com/libretro/RetroArch/v1.22.2/network/netplay/netplay_frontend.c)

以下验收主要针对常规输入帧同步；Netpacket 另立能力与验收表，联机期间不能直接沿用暂停、快进、回滚和读档能力。[固定版本接口约束](https://raw.githubusercontent.com/libretro/RetroArch/v1.22.2/libretro-common/include/libretro.h)

最低验收：真实两机与晚加入观众、延迟／抖动／丢包、拒绝2P、观众输入无效、断线清理、重置与读档、不同ROM/核心拒绝、多台电玩机并行、MC帧耗时。Windows loopback 三端通过不等于这些已通过。

## 9. 后续核心：按实际能力选择，不只看统一接口

以下是阅读时官网能力表，不是方块电玩验收结果；表中的“未承诺”不能当作明确支持。

| 平台／候选 | 官网 Netplay 标记 | 接入前重点 | 文档 |
| --- | --- | --- | --- |
| FC / Mesen | 支持 | 已有桥；补原生保存与诊断，特殊外设单测；FDS涉及额外固件 | [Mesen](https://docs.libretro.com/library/mesen/) |
| SFC / Snes9x | 支持 | 动态尺寸、非FC采样率、Multitap；MSU-1多文件资源 | [Snes9x](https://docs.libretro.com/library/snes9x/) |
| SFC / bsnes 当前主页面 | `-`，未明确承诺 | 与旧Accuracy/Balanced页面区别；性能、增强画面、子系统内容 | [bsnes](https://docs.libretro.com/library/bsnes/) |
| GBA / mGBA | 不支持 | 先单机音画/原生保存，RTC/特殊输入按需验；不要承诺掌机连线 | [mGBA](https://docs.libretro.com/library/mgba/) |
| 街机 / FBNeo | 支持 | 核心与DAT匹配、parent/BIOS/samples、输入、旋转和逐游戏验证 | [FBNeo](https://docs.libretro.com/library/fbneo/) |
| 街机 / MAME 2003-Plus | 支持 | 即时档按游戏决定；不能代表所有MAME版本 | [2003-Plus](https://docs.libretro.com/library/mame2003_plus/) |

我们的迁移建议：先选一个许可与目标明确的普通 SFC 核心，再接 mGBA 单机；街机先做小范围白名单。每个平台先验证一套最小闭环，再增加特殊附件／更多游戏。Snes9x、bsnes只是候选比较，本笔记没有作出替换授权或最终选型。

需要专门记住：

- Mesen 四人适配器需配置 User 5 为 Four Player Adapter；已有 1–4 路数字输入不代表该设备配置已接通。[Mesen 控制器](https://docs.libretro.com/library/mesen/#controllers)
- 街机 ZIP 的名称、内部校验和父集／BIOS关系可能参与识别；不要自动解压或随意改名。固定核心与对应 DAT，允许在工作台预检缺项；CHD和Samples另查目录规则。[街机入门](https://docs.libretro.com/guides/arcade-getting-started/)
- 固件可能是可选或必需，由核心和内容决定。只说明缺什么、预期路径与校验，不默认下载或随包提供商业 BIOS。
- mGBA 页面存在 AV 数值占位信息，实际参数须运行时核验；不能用网页表格替代真实加载测试。[mGBA](https://docs.libretro.com/library/mgba/)
- 本次未阅读所有核心。未来 3D、光盘和电脑平台需新增专题，不从 FC64 推断全面兼容。

## 10. 诊断、测试和发布：最先补的实用工具

官方排错重视核心／前端版本、系统、复现和日志。我们应把这些信息变成用户能理解的一段诊断，不让玩家只看到“操作未完成”。[排错](https://docs.libretro.com/guides/troubleshooting-retroarch/)、[日志](https://docs.libretro.com/guides/generating-retroarch-logs/)

建议：

- “复制诊断”包含实际选中后端、核心版本、关键资源身份、模式、设备、AV参数和失败阶段；令牌、私人路径等脱敏，输出有界。
- 接核心日志和消息回调时区分提示、警告和致命错误；C变参日志回调不能直接用不匹配的JNA签名，应单独设计安全桥并测试。
- 建立三层测试：接口正确性／同状态同输入一致性；AccuracyCoin等核心硬件精度；真实MC交互、多机与长时负载。三者不能用测试数量互相替代。
- 对刚收到的 `15/141` 图片：尚不知道实际JAR、所选后端和测试流程。后续排查需用相同测试ROM身份、相同核心二进制及选项，在参考前端与模组分别完整运行；不能现在下结论是Mesen或libretro坏了。
- 核心升级作为新运行配置验收：来源、源码对应、构建方法、SHA、兼容档案和可回退包一起记录，不静默替换旧档所需核心。

许可需逐组件核对：libretro API、RetroArch、具体核心、公共库文件、ROM/BIOS、模型素材不是同一份许可。文档分别列有 GPL、MPL 和含非商业限制的核心；不能因主模组选择 GPLv3，就认为 Snes9x/FBNeo 等所有材料自动满足分发要求。旧版 MAME 与当前 MAME 也需区别。以实际版本原始许可和精确对应源码为发布检查依据，本笔记不构成完整法律审核。[许可表](https://docs.libretro.com/development/licenses/)、[Snes9x许可](https://github.com/snes9xgit/snes9x/blob/master/LICENSE)、[bsnes许可](https://github.com/libretro/bsnes-libretro/blob/master/LICENSE.txt)、[MAME仓库](https://github.com/libretro/mame)

## 12. 建议工作顺序与完成标准

以下是后续技术路线的优先级建议，不代表相关能力已经实现。

1. **P0：身份与诊断。** 能证明实际运行哪个核心，能区分加载／依赖／模拟／画面失败；建立同版本参考前端对照。
2. **P0：保存安全。** 即时档之外补原生保存数据闭环；退出再开验证，保留卡带／个人归属和旧档保护。
3. **P1：公共API补齐。** 选项v2、输入元数据、旋转、必要目录能力；新增契约测试，不虚报支持。
4. **P1：普通SFC/GBA迁移。** 每个平台先音画、输入、保存、关闭回收；同一公共桥仍要单独实测。
5. **P1：Netplay进MC。** 接身份／席位／音画／退出保存，做真实多机，保留串流；不是用POC成功直接替换现有联机。
6. **P2：有测量依据的性能优化。** 先统计，再做追帧输出控制、重采样或拷贝优化；报告收益和边界。
7. **P2：街机范围扩展及体验项。** DAT、依赖和旋转先做；shader、实物手柄、更多外设后续按需求。

每项完成需记录：固定版本／核心与内容身份、环境、实际测试结果、未验边界、成品与回退。不把本笔记里的“可用思路”改写成对外“已支持”。
