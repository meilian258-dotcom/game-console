# FC64：通用 libretro 与 RetroArch Netplay 验证

日期：2026-09-21。适用：Minecraft 1.21.1 / NeoForge 21.1.236 及以上 21.1.x / Java 21，FC 主模组 0.31.0-alpha.64。本地测试候选已构建和冻结；不是正式稳定版。

原型包括公共父桥、FC 适配、独立通用工作进程、新旧状态与音画对照，以及真实 RetroArch 主机、玩家和观众实验。

## 范围与边界

- 保留 FC63、旧 helper、固定 Mesen、运行档案及用户存档。新 helper 使用独立资源路径。
- 公共桥支持受限的软件渲染 libretro 核心，第一项实际接入为 Mesen FC，不代表全部核心支持。
- 联机验证上游 RetroArch 实现，不把原有锁步或自制协议称为 RetroArch Netplay。
- 保留玩家串流、服务端托管及 Minecraft 权限，未验收前不切换联机路径。
- 不安装、发布、重启游戏或服务器，不运行用户 ROM，不修改世界或用户存档。

## 验收门槛

新 FC 适配器只有在固定核心、选项、控制器、状态包络一致，真实新旧普通/光枪音画 RAM 对照和双向快照恢复通过后，才可沿用 FC62/63 身份。二进制完整性独立严格校验，不删除身份检查。旧 WASM 状态不自动转换。

进程仅限回环地址，验证认证、尺寸上限、硬超时和进程回收。RetroArch 独立进程成功不等于 Minecraft 多人验收。最终成品与版本验证记录需列明实际结果及待验证项。

## 当前结果

### 本轮真正接入的内容

FC 普通手柄和光枪均改用公共 `LibretroProfile` / `LibretroProcess` 接入层及通用独立核心进程。客户端、服务端托管和私人玩法通过原来的 `NesCores` 入口选择它，不是只有独立演示程序能用。

公共层不依赖 Minecraft，负责固定核心加载、RetroPad 数字输入、软件画面、原始立体声、状态及内存读取；FC 适配层负责八键映射、光枪、原有单声道输出和旧状态包络。新核心描述包含资源和 SHA-256，不提供从玩家路径加载任意 DLL 或运行时下载核心的功能。

桥支持逐帧输入批处理和选择性返回音画；省略输出仍会正常模拟，不是跳过游戏帧。现阶段工作进程仍转换并缓存画面，节省的是进程间传输，不承诺所有渲染 CPU 都省掉。FC 日常播放仍返回正常音画，尚未改造网络追帧调度或宣称网络流量下降。RUN 与 CPU RAM 查询合并发送，避免额外一次往返。

Mesen 本体、原 helper/JNA/profile、旧 WASM、模型和正式贴图字节保留。新 helper 位于独立 `core/libretro-generic/` 路径，校验与旧存档身份分开。旧存档模式、卡带规则、2P 权限、推流和服务端托管规则未改。SFC/街机/GBA/Flash 没有迁移；通用接口不等于所有 libretro 核心已经适配。

### 安装与回退

1. 先退出游戏和测试服务端，备份完整世界及模组数据，在副本和独立配置中测试。
2. 客户端和服务端统一使用最终目录内的 `game_console-0.31.0-alpha.64.jar`；单人只换该实例。旧同 ID 主包移到 mods 外备份，不能混放两份。
3. 最终目录为 `方块电玩-通用libretro验证-FC64-20260921`。不要使用 `build/libs` 中间包；两张历史未审手柄草稿只在最终交付中恢复为 FC63 的原字节，源码中的草稿不覆盖。
4. 无需安装 RetroArch、额外运行库或调整启动器全局 IPv6。不要混装 Flash prototype.8，其依赖范围不接受 FC64。其余附属组合也未在本轮实机验收。
5. FC62/63 同 ROM、同普通/光枪模式的 libretro 状态经过双向恢复对照；FC61 及更早 WASM 状态仍隔离，不自动转换。不要清空存档来升级。回退最稳妥的方式仍是恢复旧 JAR 与测试前备份。

新子进程只连接 IPv4 回环，使用认证令牌、载荷上限、操作超时和自身进程回收。进程隔离不是操作系统安全沙箱，不应加载来源不明的原生核心。

### 自动验证与已知边界

新通用工作进程真实 Mesen 探针通过 1906 项检查，包含双实例音画/RAM、普通与光枪输入、状态、批量无输出及软件像素格式/动态几何等。公共契约新增 10 项单元测试，工厂入口/配置新增 2 项。最终 `check jar --offline --rerun-tasks` 重跑共 2241 项、0 失败、0 错误、8 项既有 Windows 符号链接权限环境跳过，构建用时 2 分 2 秒；源码、资源、构建工具捕获前后相同。冻结工具额外 16 项测试通过。

最终冻结 JAR 为 35,852,516 字节、2122 条目，SHA-256：`8F121F0F27E55E80E82EEACDC973A83E4EE860DA0CE3472B5263CD953549E600`。相对 FC63 新增 11 项，仅修改核心工厂与两份版本元数据，没有删除条目；旧 core、正式素材及语言字节全部保留。新 worker SHA：`91A0752F803D60F10910839084A49F2326998B1317F768B59F32E70C93CD6680`。`build/libs` 中间包 SHA 为 `DF9EECD7DD5C80F6BB74F12A1B37AB34BFA384ABACA542904F476D631BA76A0F`，因含两张未审草稿不作安装件。

最终 JAR 在父 JVM `java.net.preferIPv6Addresses=system/true/false` 三种设置下分别启动成功，每组都与冻结 FC63 独立比较普通/光枪 544 帧、397476 项检查。最终只读检查新旧核心工作进程残留为 0。

对照使用 SHA 固定的 FC63 冻结 JAR、隔离类加载器和原创诊断 NROM；未使用玩家游戏。覆盖正常运行音画逐位一致、双向读档、立即恢复的显示/RAM、下一帧保存输入、错误 ROM/profile/模式拒绝及私人/服务端身份规则。

读档音频有既有边界：把“连续运行的源端”和“恢复后的接收端”直接比较，会观察到声音瞬态和采样数量差异。61 帧控制实验中旧→旧、旧→新均为 61 帧音频不同、6 帧样本数量不同、19616 个样本位不同，最大差值 0.14382935；画面/RAM始终相同。双方恢复相同快照后，旧→旧与旧→新均 61 帧音频逐位相同。因此新桥没有扩大这个已观察到的差异，但不能宣称读档后与连续源端声音完全相同，也没有把此问题当作本轮已经修复。复现程序为 `LibretroAudioRestoreDiagnostic`。

Windows x64 是实际原生执行验证环境；Linux x64 资源校验保留但未执行，跨系统同步、macOS/ARM 未验收。FC 仍使用固定 NTSC 和既有 60 帧会话调度，不是新增 PAL 原速支持。Minecraft 单人/多人、航空学、光影、长时间负载和附属组合均需实机复验。

建议游戏内依次测试：普通 FC 开关机和 N/F7 提示、双手柄输入及允许/拒绝2P、个人/卡带档继续、光枪触发、两台机器并行、公开三种模式与私人模式。异常时提供本次版本、“复制诊断”和实例 `logs/latest.log`。不要把页面显示其他附属未安装误当作 FC 缺前置。

### RetroArch Netplay 实验

主机/玩家/观众实验使用上游 RetroArch 1.22.2。原生核心支持 libretro 不意味着它自己实现了 RetroArch 的网络、席位与观众协议。

本轮 MOD 仍使用原有 Minecraft 联机实现，未暴露新的 Netplay 选项。即使本机三端实验通过，也仍需接入 Minecraft 会话、玩家身份、2P权限、断线和存档，完成真实多机测试后才能交付游戏内 Netplay。原推流方式保留，不强迫旁观者全部运行本地核心。

实验只使用本机回环和原创诊断内容，不开放公网，不修改防火墙、不安装全局编译器；独立 RetroArch 可执行文件不内置到 FC64 JAR。

最终本机三端验证通过全部 18 项检查。上游 RetroArch 1.22.2 + 同一 Mesen 核心，主机、第二玩家与稍后连接的观众在 13 个共同确认帧（120～840，每60帧）状态 CRC 全部相同；主机输入 A、第二玩家输入 B 均进入游戏 RAM。观众故意全部按键，仍只有前两位的输入；观众角色为只读且不占控制端口。三端均生成真实诊断画面，最终均正常退出，所属进程残留为0。

这不是自行模仿的 Netplay。实验补丁仅限制回环地址、提供无窗口的脚本输入/节奏及观测日志，没有替换上游联机算法。早期裁剪为无 zlib 的构建在首次状态同步时崩溃；采用官方自带 zlib 构建后通过。早期1200帧实验虽校验一致，却超过35秒上限被脚本结束，不记为最终成功；最终900帧实验正常结束且保持三端不少于10共同确认帧等门槛。

仍未验证：Minecraft 网络承载/会话绑定、真实跨电脑与高延迟丢包、游戏内旁观切换、会话断线恢复和存档联动。此无窗口实验有人为节奏控制，不能拿运行耗时作为性能基准；也没有证明所有核心可联机。下一步需要把宿主音画/输入嵌回游戏，并由服务器将 Minecraft 玩家授权对应到 Netplay 席位，才能替换现有本地同步路径。
