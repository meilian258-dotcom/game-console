# 合金弹头2实时只读诊断

日期：2026-09-12。只读性能计数、线程与日志诊断；未改设置、运行库、模组、ROM 或存档，未读取或消费核心活动管道。

## 实际身份

诊断目标为 Minecraft 进程及其 `NativeCoreWorker` 子进程，内容身份为 `mslug2.zip`。采样前后复核进程创建时间、父子关系、类名和内容，避免将切换游戏后的数据混入同一次结果。

## 观测

- 首次 `jcmd Thread.print`：helper main 位于 `NativeCoreWorker$Engine.run:197` 的 `LockSupport.parkNanos`，为正常帧节流等待；命令读取线程等待输入。
- 15 组约 2.6～2.9 秒进程计数间隔，共 40.306 秒。CPU 增量以 100% 为一个逻辑核：加权平均 22.096%，区间 7.20～38.95%；不能称为整机 22%。
- helper WriteTransferCount增量平均16.3718 MiB/s，范围15.502～17.222 MiB/s；MC对应读计数持续约16MiB/s。helper工作集493～496MiB；MC约2117～2128MiB。没有测到每秒精确游戏帧率。
- 后续线程快照分别位于 JNA `retro_run` 和 `run:197` 等帧。少量快照不等于完整 CPU 采样分布，也不能排除瞬时抖动。
- 采样期间游戏日志无新增；既有身份服务 TLS 警告不能作为本次卡顿原因。
- 两进程采样结束仍为同一创建时间且存活。没有停止游戏；只结束采样命令，无后台监控。

## 判断及限制

既有运行记录描述游戏元素增多时减速，而 Minecraft 移动正常；helper 仍正常等帧、有余量且持续写出，更支持原游戏减速而非持续 CPU 饱和或管道长堵。但未取得游戏内部模拟速度与唯一样本帧计数，不能宣称满速或完全排除模组开销。

MAME官方对此游戏明确记录：原Neo Geo家用/街机硬件也有严重减速，Metal Slug X改进该问题。
来源：https://wiki.mamedev.org/index.php/Game:mslug2

本地helper输出记录为24+4*w*h+2*pcmCount字节，分辨率非固定；进程写计数也非专属视频计数。空视频回调可保留旧画面再输出，所以数据输出率不等于游戏动作更新率。没有擅自用320×224推算并宣称60FPS。

另一独立限制：`CabinetMediaStream:54` 将远端加入者／旁观视频限制为20fps，主持本地画面走直接 `emulator.pollFrame`，不受该发送限额。远端体验还需端到端网络与显示测量，不能仅凭此限制判断具体卡顿原因。

后续如需实施优化，应先增加模拟速度/主机输出/远端接收统计，或可选模拟CPU增强；不要只加Minecraft内存、修改ROM或无证据把全部卡顿归因20fps。本轮没有制作新JAR。
