# MAME 同步第二轮：同批重载与初态重放

记录者：cabinet_reuse_review；2026-09-12 10:30（UTC+8）。范围仅新增诊断源码和本目录证据。生产/helper/DLL、原实验、用户 ROM/BIOS/存档、现有进程均未修改。根代理统一维护手册留痕。

## 当前结论

存在有价值的正向结果，但**本轮仍未通过完整状态一致性验收**，不能据此开放任意 MAME 本地同步或保证冷加入/即时恢复。

| 对照 | KOF97 | mslug2 |
|---|---|---|
| A/B 相同历史至 2800 帧，同时载 A 的 2200 帧状态；之后 600 帧 | 完整画面、PCM、重存状态全等 | 全等 |
| 两端再重复同一加载/600 帧流程 | 同轮 A/B 仍全部相等 | 同轮 A/B 仍全部相等 |
| 冷实例仅 8 帧启动后载同一状态 | 画面全等，600 帧 PCM 不等 | 画面全等，前 86 帧 PCM 不等 |
| 先走相同总步数、但旧输入全部为零，再载同一状态 | 600 帧 PCM 不等 | 前 85 帧 PCM 不等 |
| 两次依次新建独立进程，32 帧时载同一初态，重放 12000 帧 | 12000 帧画面及 PCM 全等；20 个后续完整状态仍各差 2–4 字节 | 同样 |

每个比较包含真实生产 Engine 回调返回的完整 RGB、完整 PCM、尺寸/DAR/旋转/样本数。状态比较检查全部 1,029,356 字节，未屏蔽字段、静音、额外跑帧、只取部分 RAM 或把空视频算成额外一帧。初始无视频阶段显式保留空输出；每次 `retro_run` 前清本帧 PCM 计数。

`ok:true` 只代表实验执行完整；`same_reload_qualified:false` / `initial_replay_qualified:false` 才是严格准入结果。两端同历史的同批重载通过，不等于基线与重载轨迹相同，也不等于未知历史的新实例能加入。

## 精确差异与源码依据

- 两游戏 `save → load → save` 均在偏移 1028439 和 1028473–1028480 改变，共 9 字节。所有端立即 postload 的全状态相等；继续运行后冷/重复轨迹在 1029342，偶尔至 1029343 不同。
- 依次新进程初态重放时，20 个后续检查点的差异并集为 159001、159004、1029342–1029343。实际完整差异范围/有界 64-bit 标量/双方 SHA 见 JSON。未把这些位置排除出摘要。
- [固定版本 save.cpp](https://github.com/libretro/mame/blob/4fc9a9312baaf34963847f884961ad9793fbbc1d/src/emu/save.cpp#L76) 按注册名排序，裸序列化只含 32 字节头和字段值；加载完成会执行 postload。该 libretro 分支关闭结构 CRC 签名校验，不能用成功返回代替 DLL/ROM/选项/状态格式相容验证。
- [sound.cpp 的 postload](https://github.com/libretro/mame/blob/4fc9a9312baaf34963847f884961ad9793fbbc1d/src/emu/sound.cpp#L752) 重设 effects 时间并重建重采样器；实际 stream 保存了部分缓冲，但输出/effects 历史并非由这段代码全部还原。这与“相同旧历史可等、冷/不同旧历史音频不等”的结果相符；尚未证明唯一致因。
- 找到具体 RTC 恢复缺口：[upd1990a.cpp](https://github.com/libretro/mame/blob/4fc9a9312baaf34963847f884961ad9793fbbc1d/src/devices/machine/upd1990a.cpp#L65) 注册 `m_time_counter`，每秒回调却调用基类 `advance_seconds()`；[dirtc.cpp](https://github.com/libretro/mame/blob/4fc9a9312baaf34963847f884961ad9793fbbc1d/src/emu/dirtc.cpp#L123) 依据自己的 `m_register[7]` 推进并回写 counter，而该基类源码未注册这组寄存器。因此仅恢复派生 counter 不足以恢复其内部时间源。
- [machine.cpp](https://github.com/libretro/mame/blob/4fc9a9312baaf34963847f884961ad9793fbbc1d/src/emu/machine.cpp#L157) 默认读主机时间，但已有 `-rtc YYYYMMDDhhmmss` 参数。后续最小验证方向是仅在隔离 QA 固定此参数，再重跑全部音画/完整状态；当前生产 helper 的受控选项不提供该参数，本轮没有擅自启用配置文件/任意命令。
- 尾部 1029342 的值如 BCD `34 → 58` 与两实例启动间隔约 24 秒吻合；结合 `device_t` 注册名及 RTC 字段排序，可强烈怀疑 RTC 秒/分钟。**尚无运行时 registry 对照，仍明确记为推断，159001/159004 也未认定为无害。** `pe-state-schema-v1.json` 只读实证现 DLL 26 个导出、COFF 符号数 0，无 `indexed_item`/注册表导出。需要带 schema 的独立诊断构建才能完整命名每个偏移，不应硬编码屏蔽未知字节。

## 初态完整重放的实际成本

固定 32 步初始化、共享同一早期 snapshot、完整重放 12000 帧（约 202.75 秒游戏）。不是中途任意快照恢复；必须保留之后每帧 4 端口输入，以及任何 reset/选项/加载事件。

| 游戏 | 冷重放耗时 | 速度/原速 | 12000 帧数据量 |
|---|---:|---:|---:|
| KOF97 | 22.82 秒 | 8.88× | 96,000 字节输入 + 1,029,356 字节初态 |
| mslug2 | 24.09 秒 | 8.42× | 同上 |

计时包含每帧完整 hash、每 600 帧完整状态与临时文件 I/O，单独串行 QA JVM，不代表 Minecraft 中一定能达到该速度。线性推算一小时历史重放约 405/428 秒；这是估算而非一小时实测。主机继续运行时，当前短历史的追赶估算约 25.7/27.3 秒；低性能机器若步进速度不高于游戏帧率则无法追赶。历史内存不是首要障碍，冷恢复延迟与尚未解决的状态差异才是。
